# Events

Площадка мастеров и мероприятий: Laravel-API и Nuxt-клиент.

```
events/
├── server/          Laravel 13 + Sail — API, Sanctum, роли
└── client/          Nuxt 4 + Nuxt UI — админка
```

## Запуск

Сервер (Docker):

```bash
cd server && ./vendor/bin/sail up -d && ./vendor/bin/sail artisan migrate --seed
```

API поднимается на `http://localhost:8001`. Порты вынесены в `.env`, чтобы
проект не конфликтовал с соседними: приложение `8001`, MySQL `3307`,
Redis `6380`, Vite `5174`.

Админка:

```bash
cd client && pnpm install && pnpm dev
```

Открывается на `http://localhost:3010`.

### Учётные записи

Сидер заводит 16 человек: одного администратора, пятерых мастеров
и десять участников. Три адреса названы по роли — под ними заходят руками,
и угадывать, кем ты вошёл, не приходится. Пароль у всех `password`.

| Адрес                | Роль          | Куда попадает после входа |
|----------------------|---------------|---------------------------|
| `admin@example.com`  | администратор | `/admin`                  |
| `master@example.com` | мастер        | `/master`                 |
| `user@example.com`   | участник      | `/cabinet`                |

Остальные — со случайными адресами: на них видно, как списки ведут себя
с настоящими данными, а не с тремя ровными строчками. Каждый из пяти
аккаунтов-мастеров привязан к своему профилю на витрине, и первый из них
достаётся `master@example.com` — под ним заходят чаще всего, и его витрина
должна быть непустой.

### Вход

Форма входа одна на всех, а кабинет у ролей разный — поэтому адрес
назначения считается после входа, по старшей роли человека. Гость, которого
развернули с закрытой страницы, после входа возвращается именно туда.

На экране входа есть селект с готовыми учётками: он подставляет логин
и пароль, чтобы не набирать их при каждой смене роли. Показывается только
в разработке — на боевой площадке список учёток на экране входа означал бы,
что зайти под администратором может кто угодно. Включается принудительно
через `NUXT_PUBLIC_DEMO_LOGIN=true`.

## Клиент

Обычное Nuxt-приложение, весь код — в `client/app`. Витрина живёт в корне
адресов, кабинет — под `/admin`:

```
app/
├── components/
│   ├── site/        Header, Footer, CtaBand — обвязка витрины
│   ├── showcase/    MasterCard, EventCard, LeadForm
│   ├── users/       Table — таблица кабинета
│   ├── Botanical*   ботаническая графика вместо отсутствующих снимков
│   └── App*         сайдбар и меню пользователя в кабинете
├── composables/     useAuth, useApiClient, useShowcaseApi, useAdminNav, useUsers*
├── layouts/         default (витрина), cabinet (кабинеты), auth (вход)
├── middleware/      role — пускает в раздел только свою роль
├── pages/
│   ├── index        главная
│   ├── masters/     каталог и страница мастера
│   ├── events/      афиша и страница мероприятия
│   ├── admin/       кабинет администратора
│   ├── master/      кабинет мастера
│   ├── cabinet/     кабинет участника
│   └── auth/        вход и отказ в доступе
├── plugins/         token-storage — токен в cookie, чтобы работал SSR
├── types/           формы ответов API
└── assets/css/      main.css + theme.css
```

### Формы

Форма кабинета разложена на две половины: слева одно занятие, справа
другое, у каждой свой заголовок (`FormSection`). Простыня полей во всю
ширину читается как список вопросов без порядка, а пара озаглавленных
колонок сама говорит, что заполняют вместе. На узком экране половины
складываются одна под другую.

Кнопки экрана — публикация, «Сохранить», «Отмена» — стоят в верхней панели
рядом с заголовком: они одни на все вкладки, и внизу длинной формы за ними
пришлось бы возвращаться прокруткой. Приезжают туда телепортом, потому что
живут состоянием формы, и только на клиенте: серверная разметка телепорта
уезжает мимо цели, и после гидрации Vue пересобирал бы панель заново.

Даты мероприятия выбираются одним календарём на два месяца: двумя полями
человек выбирал вслепую — чтобы понять, попадает ли программа на выходные,
приходилось открыть один календарь, запомнить, закрыть, открыть второй.

Дни расписания не заводятся руками: они и есть даты мероприятия. Написанное
хранится по дням и переживает сдвиг дат — человек двигает их, пока подбирает
удобные, и терять при каждом сдвиге всё написанное нельзя. Вернул дату —
вернулось и расписание на неё.

### Цвета и шрифты

Forest — основной цвет площадки, coral — акцент действия: коралловым
помечается кнопка, ради которой написана страница. Раздать его целым
секциям — значит завести площадке второй бренд. Обе шкалы объявлены
в `theme.css` и подключены к Nuxt UI как `primary` и `secondary`,
поэтому кабинет и витрина живут на одной паре.

В светлой теме обе смещены на ступень 700: пятисотые на кремовом фоне
выглядят подсвеченными, а коралловый в 500 рядом с зелёным уходит
в морковный. На тёмном фоне кабинета те же 700 сели бы почти в цвет
подложки, поэтому сдвиг только для светлой темы.

Roboto для текста, Roboto Condensed для заголовков, кириллический сабсет.
Шкала кегля поднята на ступень (база 17px) — но через `--text-*`, а не
через `font-size` у `html`: отступы в Tailwind заданы в rem, и разгон
корня раздул бы вместе с текстом всю вёрстку.

Авторизация — токеном Sanctum: клиент живёт на своём origin, сессионных
cookie у него нет. Токен лежит в cookie `auth.token`, поэтому серверный
рендер сразу знает, кто пришёл, и страница не мигает гостевым состоянием.

## API

| Метод  | Путь                     | Доступ            |
|--------|--------------------------|-------------------|
| GET    | `/api/home`              | все               |
| GET    | `/api/masters`           | все               |
| GET    | `/api/masters/{slug}`    | все               |
| GET    | `/api/events`            | все               |
| GET    | `/api/events/{slug}`     | все               |
| POST   | `/api/leads`             | все               |
| GET    | `/api/leads/check`       | все               |
| POST   | `/api/login`             | все               |
| POST   | `/api/logout`            | по токену         |
| GET    | `/api/user`, `/api/me`   | по токену         |
| GET    | `/api/admin/users`       | роль `admin`      |
| GET    | `/api/admin/users/{id}`  | роль `admin`      |
| GET    | `/api/master/overview`   | роль `master`     |
| GET/POST | `/api/master/profile`  | роль `master`     |
| GET/POST | `/api/master/events`   | роль `master`     |
| GET/POST/DELETE | `/api/master/events/{id}` | владелец |
| GET    | `/api/master/leads`      | роль `master`     |
| GET    | `/api/master/leads/{id}` | владелец          |
| PATCH  | `/api/master/leads/{id}/status` | владелец   |
| GET/PUT | `/api/cabinet/profile`  | по токену         |
| GET    | `/api/master/reviews`    | роль `master`     |

Правка мероприятия и профиля идёт `POST`, а не `PUT`: форма несёт файл,
а `multipart` в `PUT` браузер не отправляет. Роль открывает раздел, но право
на конкретную запись проверяет политика — у мастера может не быть витрины,
и тогда править ему нечего. Владелец мероприятия при правке не меняется:
иначе администратор, поправивший чужую опечатку, перевёз бы мероприятие
на свою витрину.

Список пользователей принимает `page`, `perPage` (не больше 100), `search`,
`sort` (`id`, `name`, `email`, `created_at`), `direction` и отвечает
`{ data, meta }`. Ключи ответов — camelCase: их читает TypeScript.

Адреса клиентов, которым разрешены запросы, перечислены в `FRONTEND_URLS`
(server/.env). Именно перечислены, а не `*`: клиент шлёт запросы с
`credentials: 'include'`, и на звёздочку браузер отвечает отказом.


```bash
cd client && pnpm lint && pnpm typecheck && pnpm build
```

Витрина открыта гостю целиком: каталог мастеров и цены — это то, за чем
человек приходит, и требовать вход, чтобы их посмотреть, значит терять его
до того, как он что-то увидел.

Цены форматирует сервер: одна и та же сумма должна выглядеть одинаково
на карточке, на странице мероприятия и в письме.

## Кабинет мастера

Работает целиком:

* **Обзор** — новые заявки, что на витрине, черновики, оценка и ближайшая
  дата с набором. Считаем то, на что можно отреагировать сегодня;
  «всего мероприятий за всё время» — красивое число, по которому нечего
  сделать.
* **Моя страница** — имя, описание, город, биография, портрет и обложка,
  переключатель показа в каталоге. Витрина заводится сама при первом заходе
  и создаётся скрытой: показывать в каталоге страницу без описания
  и мероприятий — плохая услуга и человеку, и каталогу.
* **Мои мероприятия** — создание, правка, удаление, публикация и снятие
  с неё, программа по дням. Черновики и прошедшее видны здесь же: кабинет —
  рабочий стол, а не витрина.
* **Заявки** — таблица с поиском, фильтрами по статусу и мероприятию,
  сортировкой и постраничной выдачей: заявки копятся быстрее всего
  остального, и через месяц «просто список» становится лентой, по которой
  ничего не найти. Контакты видны целиком — заявка существует ровно затем,
  чтобы по ней перезвонили.
* **Отзывы** — только чтение, включая те, что на проверке. Своё мнение о себе
  мастер не правит: иначе оценка перестаёт что-либо значить.

### Статусы заявки

Пять: новая, тёплый, бронь, возврат, спам. Набор короткий намеренно —
каждое состояние что-то меняет для мастера или для мероприятия. «Тёплый»
означает разговор, который идёт: место ещё не занято, но и забывать
о человеке нельзя.

Цвет статуса приходит с сервера вместе с ним: иначе список статусов задан
в одном месте, а их вид — в другом, и новый статус появляется на экране
серым, пока кто-нибудь не вспомнит про вторую таблицу соответствий.

Бронь занимает место в группе, возврат его освобождает. Занятые места
считаются по броням, а не хранятся счётчиком: счётчик расходится с заявками
при первом же двойном переводе, и восстановить его потом неоткуда. Когда
мест не осталось, перевод в бронь отклоняется — и проверяется это в момент
перевода, а не при показе списка: между открытием экрана и нажатием кнопки
последнее место мог занять кто-то другой.

Смена статуса идёт отдельным окном с комментарием, и каждая записывается
в историю. Через месяц «почему сняли бронь» не помнит никто, а место
к тому времени уже занято кем-то другим.

У заявки есть своя страница — `/master/leads/{id}`: контакты, сообщение
и вся история переходов лентой. Отдельным экраном, а не раскрытой строкой:
история со временем длиннее самой заявки, а на страницу можно дать ссылку.
Быстрая смена статуса осталась и в списке — за ней не нужно никуда уходить.

## Кабинет участника

**Мои данные** — имя и телефоны. Номер у человека не один: рабочий, личный,
номер того, кто едет вместе, — поэтому телефоны лежат отдельной таблицей,
а основной помечен. Вошедшему форма заявки подставляет имя, почту
и основной номер; если номеров несколько, в форме появляется выбор.
Остаётся написать сообщение — переписывать свои же контакты в каждой заявке
человек не должен.

Заявка вошедшего остаётся привязанной к его аккаунту. Маршрут открыт гостю,
охраны на нём нет, поэтому токен разбирается в самом контроллере: иначе
своих записей человек потом не нашёл бы.

### Одна заявка на мероприятие

Вторую не принимаем: мастеру достаются два одинаковых контакта, а человек
не понимает, дошла первая или нет. Вошедшего узнаём по аккаунту, гостя —
по метке, которую хранит его браузер, и обоих — по телефону: браузер человек
мог сменить, а номер в заявке пишет тот же.

Метка вместо сессии: API работает по токену и без состояния, а заводить
сессию ради одной проверки — это куки между доменами и вся возня с ними.
От злого умысла это не защищает: почистить куки может каждый, — но от второго
нажатия кнопки защищает, а больше и не требуется.

Страница спрашивает об этом при открытии и показывает не форму, а отметку
«вы записаны»: узнать о повторе, заполнив всю форму, — худший момент
из возможных.

Картинки хранит spatie/medialibrary на публичном диске (`storage:link`).
Портрет, обложка витрины и обложка мероприятия — коллекции по одному файлу:
новая загрузка сама заменяет прежнюю, а вместе с моделью уходят и её файлы.
Уменьшенные копии делаются сразу, а не через очередь: воркер под неё
не поднят, и отложенная копия просто не появилась бы. Наружу отдаётся полный
адрес — клиент живёт на другом домене и «/storage/…» попросил бы у себя.

Галерея мероприятия — отдельная коллекция, и порядок в ней хранится: это
порядок кадров на странице, а не время загрузки. Форма присылает её целиком,
уже сложенную: снимок, который остаётся, обозначается одним id, новый
приходит файлом, чего нет в списке — то удалено. Так перестановка десяти
кадров не превращается в десять перезаливок.

Программа мероприятия переписывается целиком в одной транзакции: половина
сохранённого расписания хуже, чем несохранённое.

## Что дальше

Готовы инфраструктура, витрина и кабинет мастера. В кабинете участника
работают свои данные и телефоны, в кабинете администратора пока только
таблица пользователей.

Не перенесено осознанно и ждёт своей очереди:

* **Видео.** Ролики мастеров живут на YouTube, и заливать их второй раз к нам
  значит платить за хранилище и писать свой плеер ради того, что уже
  раздаётся. Хранить их нужно ссылкой, а не файлом, — это отдельная сущность,
  а не ещё одна коллекция картинок.
* **Галерея у витрины мастера.** У мероприятия она есть, у страницы мастера
  пока обложка и портрет: собирать вторую галерею стоит, когда станет ясно,
  показывает она место или людей.
* **Мои записи у участника.** Заявка уже привязана к аккаунту, поэтому
  экран собирается из готового: показать, куда человек записался, когда
  начало и сколько осталось доплатить.
* **Отзывы от участника.** Показываем проверенные, форма отправки появится
  вместе с кабинетом участника: право оставить отзыв проверяется по заявке.
* **Разметка для рекламных кабинетов.** Отдельный этап со своим сервисом,
  а не колонки, лежащие мёртвыми в таблице заявок.
